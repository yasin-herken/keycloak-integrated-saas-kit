# Enterprise SaaS Kit - Global Agent Rules (RULES.md)

## 1. Architectural Boundaries and Constraints
* The system will be designed as a "Modular Monolith". The complexity of microservices will be strictly avoided during the MVP phase.
* The core technology stack is locked to the targeted versions: **Java 25, Spring Boot 4, Spring Security 7, Keycloak 26+, and PostgreSQL (Latest)**.
* The backend will serve exclusively as a REST API (Resource Server) using Java and Spring Boot.
* The frontend template (React/Next.js) will be treated solely as "dumb components". Strictly **no refactoring** will be done on the UI code for performance or "clean code" purposes. State management in the UI must be kept to an absolute minimum. (This is out of scope for now, as no frontend development will occur during the MVP phase).
* All authentication and authorization processes will be handled by Keycloak. No custom authentication or authorization logic will be written in the backend.
* All API endpoints will be secured and verified using JWT/JWE (Bearer Tokens) generated by Keycloak. Token validation on the backend will be handled natively via Spring Security.
* Package naming conventions must strictly follow the `com.archcore` organizational structure and standards.
* The use of **Lombok** is STRICTLY MANDATORY in DTO, Entity, and configuration classes to eliminate boilerplate code.

## 2. Security and Identity Management
* User passwords will absolutely not be stored in the application database.
* All authentication, token generation, and Google Login processes will be managed through an isolated Keycloak server.
* API and client communication will be completely stateless, relying exclusively on Bearer Tokens.
* CSRF vulnerabilities will be neutralized in Spring Security configurations by establishing a strictly stateless architecture. XSS protection will be enforced via text sanitization (escaping) within the Jackson serializer.

## 3. Execution Limits
* The agent is authorized to write code **only** within the scope specified in the active task file located in the `.tasks/` directory. The agent cannot take the initiative to refactor, add features, or delete code in files outside the scope of the current task.
* Infrastructure changes (docker-compose, Kubernetes manifests, or ArgoCD configurations) can only be executed by the `infra-agent`.

## 4. MCP (Model Context Protocol) and Documentation Mandate
* Agents (especially the `codegen-agent` and `infra-agent`) must not rely on memorized or outdated information before generating code or configurations.
* Official documentation for the targeted technologies (Java 25, Spring Boot 4, Keycloak 26+) must be dynamically queried using MCP tools (`doc-fetcher`, `web-search`).
* Pulling documentation is strictly mandatory for the following topics:
  - Keycloak container import/export commands, SPI implementations, and environment variables.
  - Spring Security 7 OAuth2 Resource Server stateless (Bearer Token) configurations.
* The agent must explicitly state the current documentation source (URL or reference) it relied upon for the generated configuration or code in the commit message or the execution output report.

## 6. Version Control (Git) and IDE Standards
* **.gitignore Rules:** Build outputs (`target/`, `out/`, `build/`), IDE configuration files (`.idea/`, `*.iml`), environment variables (`.env`), and secret keys/certificates (e.g., `*.pem`, `*.key`) MUST NOT be committed. If the agent generates such temporary or sensitive files, it is responsible for instantly adding them to the `.gitignore` file.
* **VCS Integration:** Every single new file generated by the agent must be immediately added to Git tracking (Add to VCS). No source code file should ever be left in an "unversioned" state or excluded from commits in IntelliJ IDEA or similar IDEs.

## 7. Clean Code and Engineering Standards
* **Clean Code Adherence:** All generated backend code must strictly adhere to Clean Code principles. This includes:
  - **Meaningful Naming:** Variables, methods, and classes must have clear, intention-revealing names without needing inline comments to explain what they do.
  - **Single Responsibility (SRP):** Functions and classes must do one thing and do it well. Large methods must be broken down into smaller, highly cohesive private methods.
  - **Error Handling:** Avoid returning `null`. Use proper custom exceptions and handle errors gracefully without cluttering the business logic.
  - **DRY & SOLID:** Eliminate duplication and ensure the architecture respects SOLID principles, maintaining a clean separation of concerns within the Modular Monolith structure (e.g., isolating domain logic from infrastructure adapters).
* *Note: As stated in Rule 1, these clean code standards apply strictly to the backend. The frontend remains exempt.*

## 8. Execution Logging and Pattern Rationale (Mandatory Output)
* **Post-Task Reporting:** After completing any development task, the agent MUST generate a structured log/report detailing the execution. This report must be presented to the user and include:
  1. **Task Summary:** A brief recap of what was implemented or modified.
  2. **Applied Patterns:** Explicit listing of any software design patterns (e.g., Strategy, Factory, Repository, Facade, Builder) utilized during the implementation.
  3. **Architectural Rationale:** A clear, engineering-focused explanation of *why* those specific patterns and approaches were chosen. The agent must justify how the chosen implementation aligns with Clean Code principles, system performance, and the overarching Modular Monolith architecture.
